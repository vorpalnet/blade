Build a B2BUA in BLADE

By the end you will have a working back-to-back user agent — an app that sits between two phones and bridges a call from a caller (Alice) to a callee (Bob) — deployed to your OCCAS domain, with a real call flowing through it and the whole SIP exchange traced in your log.

You will write four small Java classes and touch three config files. No prior BLADE experience is assumed — you should be comfortable with Java and know what a SIP INVITE is. We build the test-b2bua app itself; to make it your own, swap the name wherever it appears.

About 30 minutes

Before you begin

Three things need to be in place:

  • An OCCAS domain you can deploy to. No domain yet? Work through INSTALLING.md first.
  • The BLADE repo, built once — from the repo root, ./build.sh. This installs the framework your app compiles against.
  • test-uac and test-uas deployed to the same domain. These are your Alice and Bob: one places calls, the other answers them.

Create the module directory and change into it:

mkdir -p test/test-b2bua/src/main/java/org/vorpal/blade/test/b2buacd test/test-b2bua

Step 1A servlet that dispatches

Every BLADE app starts with one servlet. Its whole job is to look at each inbound SIP request and hand it to the right callflow — a small class that handles one exchange.

The class extends AsyncSipServlet — the framework's base servlet, which does the SIP plumbing and calls your chooseCallflow for each new request. That method is the entire routing table: an INVITE sets up a call, a CANCEL tears a setup down, everything else is a straight passthru. The annotations (omitted above) include @SipApplication(distributable = true) — the one that replicates SIP sessions across the cluster, so a call survives a node failing.

Note

Your editor will flag the three callflow classes as missing. That's expected — you write them next.

Step 2The INVITE callflow — the heart

This is the class that bridges the call, and it's where BLADE's whole idea lives.

Read it top to bottom — it runs in the order the messages arrive. createRequest clones Alice's INVITE into one aimed at Bob and links the two dialogs; sendRequest sends it and hands your lambda Bob's response when it arrives; createResponse builds Alice's answer from Bob's; and the ACK is passed on to Bob. In classic SIP servlet code that exchange is scattered across a doInvite, a doResponse, and a doAck with state variables between them. Here it is one method.

Between each step the callflow's state serializes into the SIP session and the method returns — so when Bob's response lands, the framework wakes your lambda back up on whatever cluster node the container routed it to. That is why the call survives failover.

Note

The sendRequest lambda fires more than once — once for the 180 Ringing, again for the 200 OK. You never test which; you just build whichever response back to Alice. When her ACK arrives through sendResponse, the exchange is complete.

Watch out

servletDestroyed is not optional. unregister() tears the JMX MBean back down when the app undeploys. Leave it out and every redeploy leaves a stale MBean registered — the loop you'll spend the most time in while developing.

Step 5Build and deploy

From the repo root, build (a dev build drops test-b2bua.war into a flat dist/), then deploy — <env> is your profile name under ~/.blade/:

./build.sh./deploy.sh <env> test-b2bua.war

Watch the server log as it deploys. The first thing you should see is your refreshed() method firing on the initial config load:

Step 6Place a call and watch it flow

Use test-uac to originate a call toward test-b2bua, with test-uas as the destination — Alice calling Bob through the app you built. The exact trigger is in test-uac's README. Now watch the log: BLADE draws each call as a sequence diagram.

You should see

The INVITE go out to Bob, the 180 and 200 come back, and the ACK go on — the outbound createRequest, the createResponse back to Alice, the sendAcknowledgement on to Bob. The call is up.

What you built, and where to go next

You wrote a working B2BUA: a servlet that dispatches by method, three callflows that own one exchange each, and a config file you can edit live. The whole call setup was one method you read top to bottom, and it runs across a cluster without you touching a thread.

  • Change the call. Add a header in TestB2buaInvite before sendRequest, or reject a call by returning early. The callflow is ordinary code.
  • Read the README for the reference view of every piece you just wrote.
  • When you're ready to stop writing the plumbing, the framework's B2buaServlet packages exactly these three callflows, already hardened for the hard cases (a CANCEL racing a 200 OK, re-INVITEs, PRACK). You extend it and implement six lifecycle callbacks instead — and this app is what those callbacks sit on top of, which is why you built it by hand first.
