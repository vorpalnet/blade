			How the iRouter works
			
		

		

			

				
The pipeline

				
When an INVITE arrives, the iRouter runs an ordered list of
				connectors. Each one pulls values out of somewhere — the SIP message
				itself, an in-memory table, a REST API, a database, a directory — and stores them as
				named variables. The pipeline never makes the routing decision; it
				gathers the facts the decision reads. "Gather the facts, then make the decision" is
				the whole model.

				
Everything a connector extracts is available downstream as
				${name} — in later connectors' URLs and queries, in routing keys and
				when clauses, and in the Route's URI and header templates.

			

			

				
Connector types

				
sip — reads the SIP request itself; no I/O. Its selectors pull
				headers, the Request-URI, or transport facts (originIP,
				transport, …). Almost every pipeline starts with one.

				
table — looks a variable up in one or more translation tables and
				spreads the matched row's values into variables (customer identity, tier, API keys).
				First table that matches wins.

				
rest / jdbc / ldap — fetch enrichment data from an external
				service, database, or directory, then run selectors over the response. In production
				these run asynchronously off the container thread; in a dry-run they execute inline
				and really contact their backends.

			

			

				
Selectors

				
A selector pulls one value out of whatever its connector produced and stores it
				under the selector's id — the variable name you reference later as
				${id}. attribute takes a value verbatim;
				regex matches named groups — (?<user>[^@]+) —
				storing each group as its own variable plus an optional rendered
				expression; json / xml / sdp extract by JsonPath,
				XPath, or SDP field; table classifies an already-extracted value.

			

			

				
Translation tables and match strategies

				
A table has a keyExpression (a ${var} template producing
				the lookup key), a match strategy, and rows. hash is exact;
				prefix is longest-prefix (dial plans); range
				matches integer intervals (8-17 for business hours). A matched row's
				values all become variables.

			

			

				
The routing decision

				
After the pipeline completes, exactly one routing strategy reads
				the variables and produces a Route. table is a key-driven lookup —
				the routing analog of a dial plan. conditional is an ordered
				if/else-if chain of boolean expressions (${action} == allow &&
				${shift} == business); the first clause that's true wins, with an optional
				default. direct always produces the same Route — useful when the
				pipeline's templating does all the work. No decision means the router answers
				503.

			

			

				
Routes

				
A Route either forwards (a requestUri, proxied
				downstream — leave it empty to forward to the inbound Request-URI unchanged) or
				responds (a statusCode like 603 Decline —
				the call ends here, no downstream dialog). Either way it can stamp headers, plain or
				conditional (when: ${customerTier} == premium), all
				${var}-resolved at decision time.

			

			

				
Dry-run, Save, Publish

				
The dry-run always uses your unsaved draft: paste a request, and the
				decision panel states in words what production would do — the resolved forward URI or
				final response, the stamped headers (with skipped conditional headers listed), and
				every variable the pipeline extracted. Nothing is proxied.

				
Save validates the document exactly as the iRouter would load it,
				keeps the previous file in version history, and writes irouter.json.
				Publish tells the running iRouter nodes to reload what was last
				saved. Logging, session settings, and per-cluster overlays are edited in the
				Configurator — both tools share the same file politely.
