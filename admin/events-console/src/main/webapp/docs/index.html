Events

What problem this solves

An event in BLADE used to be four hand-written things that nothing checked against each other: the destination, provisioned by a WLST script; the publisher's JNDI constants; a consumer with a hand-typed message selector; and a payload shape that existed nowhere at all.

The failure that motivated all of this

A message selector is a quoted string literal. No compiler checks it. A consumer whose selector does not match what the publisher stamps receives nothing — and that is indistinguishable from no events being published. People lose days to it.

Now one declaration in the catalog is the source of truth, and the selector, the payload class, the JSON Schema, the consumer skeleton and the ingress validation are all derived from it.

Catalog

The catalog is domain-wide and lives at config/custom/vorpal/events.json. Publishing writes it through the versioned file store — every publish keeps a backup — and the engine tier picks it up with no redeploy.

It also carries the event types BLADE itself emits: the application and session lifecycle, session keys, and call events. Those used to be described only by their extraction rules in each app's analytics config, which says where a value comes from but never what shape it is.

Contract here, extraction there

Deliberately split. The catalog is the contract — what an event is called, what fields it has, where it flows — and it is domain-wide. The extraction rules stay per-app in analytics.events, because the same logical event legitimately comes from different headers in different applications. The Catalog page cross-checks the two and reports drift.

Designer

Describe the fields once; take away the payload class, its JSON Schema, a consumer already bound to the right selector, a producer snippet and a sample envelope. Or download the lot as a Maven module.

Wire names are preserved exactly. A field named when_text becomes a Java whenText property carrying @JsonProperty("when_text") — the bytes on the destination never change shape to suit Java naming.

The server generates source and stops there. It does not compile it and does not publish a jar into the shared library: the wire contract for this bus is the JSON Schema, which is what keeps a consumer written in another language a first-class citizen.

Destinations

The domain's JMS resources with their live numbers — depth, pending, received, consumers — plus every durable subscription and the selector it actually subscribed with.

A distributed destination has one runtime MBean per member; the console sums the counters and reports the destination as a whole, because that is the question an operator is asking.

One stack, not two

Analytics and the event bus used to be provisioned by two scripts that were the same six steps with different names and identical connection-factory settings — two file stores, two JMS servers, two modules and two subdeployments, for one queue and one topic.

They are now one: configure-messaging-jms.py. On a domain that already has the analytics stack it adopts it and adds the topic, rather than renaming anything — WebLogic cannot rename a JMS resource, and destroy-and-recreate would orphan the file store. Every JNDI name is unchanged. Each destination gets its own quota, so one cannot starve the other out of the shared store.

Troubleshooting

A consumer receives nothing

Check the Destinations page for its durable subscription and compare the selector against the catalog. The Catalog page reports this automatically as selector-drift. A subscription with a growing pending count and an old last-received time is the signature.

The destinations page is empty or errors

The console reads JMX on the AdminServer. If it cannot, the reason is shown verbatim on the page rather than hidden behind a 500. The most common cause is that the JMS resources have not been provisioned yet.

Publishing appears to do nothing

An application only opens a connection to the bus when its own events.enabled configuration says so — off by default, so an app that does not publish never holds a JMS connection. Check that block in the Configurator before looking further.
