See the code behind the call

A callflow is how a BLADE application expresses a whole SIP conversation. Instead of the traditional JSR-289 model — where the logic for one call is scattered across separate doInvite, doResponse, doAck, and doBye handlers that you have to mentally reassemble — a callflow is a single process(...) method you read top to bottom, the same order the messages happen.

The lambda-continuation model

The trick is that each response handler is a lambda passed to the request that provokes it. You call sendRequest(request, response -> { ... }), and the lambda runs when that response arrives; inside it you sendResponse(response, ack -> { ... }), and so on. The conversation nests exactly as it flows: 

sendRequest(bobInvite, bobResponse -> {
    SipServletResponse aliceResponse = aliceInvite.createResponse(bobResponse.getStatus());
    copyContentAndHeaders(bobResponse, aliceResponse);
    sendResponse(aliceResponse, aliceAck -> {
        sendRequest(copyContentAndHeaders(aliceAck, bobResponse.createAck()));
    });
});

That is a full back-to-back call bridge. The response lambda even fires more than once — once for 180 Ringing, again for 200 OK — without you writing a state machine. Behind the scenes the framework serializes the continuation into the SIP session, so a paused callflow survives node failover across the cluster.

The Source tab is the real code

When you pick a traced step, the Source tab shows the real source of the app that handled it — copied out of the framework and service tree when the app was built, not a hand-written snippet — with the exact line that sent the message marked. So it can't drift from the code that actually runs, and it works the same for framework flows, BLADE services, and customer-built apps.

Callflow vs. Flow

The Flow editor shows inter-app routing — which application FSMAR hands a call to. The Traces tool shows intra-app conversation — what each application does once it's handling the call. Flow is the map; a callflow is the trip.

Traces — the flight recorder

The Traces page is the heart of this tool. Arm a rule (match a header pattern, cap the capture count), reproduce the call, and read the recording: the SIP messages coming and going through every BLADE app in the chain — raw message text included — merged into one timeline, with each sent message pinned to the exact source line that emitted it. Arming is in-memory runtime state on the Trace MBeans — it never touches configuration and disappears on restart.

The detail panel on the right has three tabs: Sequence, Message and Source. Picking a call opens the Sequence tab; picking a step updates all three but leaves you on whichever tab you are viewing. The Sequence tab draws the same steps as a ladder diagram — one lifeline per party (each BLADE app boxed, the external softphones dashed) and one arrow per message hop, in time order. An arrow whose message carries a session description is labelled (SDP), as in INVITE (SDP). A message crossing an app is logged twice — the app that sends it and the next app that receives it — and the two are matched by Call-ID (the reliable per-hop key) into a single arrow between their two lanes. The receive is often logged first: a send is recorded once the container returns from sending it, and an app on the same engine has taken the message by then; a routed call lays out caller → app₁ → … → appₙ → callee and the responses flow back. The external softphone names come from the From/To headers only at the true ends of the chain (they are end-to-end, so they can't name an internal hop). The timeline and the diagram are linked both ways: click a step on the left and its hop lights up; click a hop and its step is selected, its raw SIP message also opens in a window over the diagram, and the Message and Source tabs follow along. Close the window with its button, Escape, or a click outside it.

HTTP steps

A traced call also shows the HTTP messages that drove it, as arrows labelled HTTP: the REST request that placed or changed the call and its response (an HTTP client lane); each callout a REST connector made while routing it, with the OAuth token fetches those callouts needed; and the transfer service's webhooks. Each callout runs to a lane named for the host it called. A request joins a call when the thread serving it sends that call's SIP, so a tpcc POST sits just before the INVITE it caused. Requests that send no SIP, and every request while no rule is armed, are not recorded. Credential headers (Authorization, cookies, API keys) are masked before anything is saved, and so are the secrets and tokens in a token fetch's body. Each application records its HTTP steps once it is running a framework build that has this feature.

The Source tab works for HTTP steps too. A request that came in opens on its resource method, at the line that was running when it sent the call's SIP. Its response opens on the line that answered it: for tpcc, the callflow line that resumed the waiting request when the call connected. A resource that answers before it returns opens on the method itself. A callout opens on the framework line that sent it, and the timeline names the connector, token fetch or webhook behind it.

Recorded calls

Recorded Calls shows calls nobody armed a rule for. Every BLADE SIP application keeps a small ladder of each call in memory and writes it to the analytics database only when the call goes wrong or is dropped, with a verdict saying whose fault it was. A recorded call has no message text and no source lines: the recorder keeps the time, direction, method or status and far end of each message, and the call's From, To and P-Asserted-Identity once, from its first INVITE, so a complaint about a number finds its call.

Every call that went wrong is kept, so the list is searched on the server and read 50 records at a time, newest first, with Load older for the next page. Narrow it by when it was recorded (the last 24 hours to start), what went wrong, whose fault it was, the application, part of the far end's address, or one call's Vorpal-ID, which finds that call however old it is, or part of a number, for a viewer whose access includes content. The search is kept in the page's address, so a filtered view can be bookmarked or sent to someone.

Who sees what

Two settings decide it, the same two the dashboard takes. The grants decide which calls a viewer sees: one entry per group, naming the domains, tenants and departments whose calls the group sees. The access policy decides what may be read in them: an ordered list of rules, the same rules the Recordings app reads, where a rule granting phi:transcript lets its groups read the text. A rule may match a call's domain, tenant and department, so a department can read its own parts of a call and not the rest. The server applies both to everything it sends, live captures, recorded calls and saved calls alike, so the browser never receives what a viewer may not see. An HTTP step is shown with the rest of its call, and its text with the call's.

Content is the SIP message text, a recorded call's parties, and the patterns of armed rules. A viewer without it still sees every arrow, its timing and the line that sent it; the Message tab says the text is hidden. Searching recorded calls by number, and seeing rule patterns, need a rule with no match: one that lets the viewer read every call they see. Saving or deleting a call needs all of it, text included, so a narrower viewer cannot replace a saved call with the part they were shown. With no grants configured, the WebLogic admin roles see every call; the policy starts out letting the WebLogic administrator groups read them, as before. That rule holds only for a WebLogic sign-in, because an identity domain's own Administrators group is a different group with the same name. When a viewer's access is limited, the page says what it covers under the toolbar.

Trace takes the dashboard's sign-in: with the identity domain configured, a tenant's people sign in there and need no WebLogic account, and the WebLogic login still works beside it. Reading is for everyone the grants show calls to. Arming, disarming and clearing, saving or deleting a call, seeing the armed rules, and the Source tab need a WebLogic admin role, because a rule captures calls on every server and the source is every application's deployed code. The page leaves those controls out for anyone else, and the server refuses them.

Snapshots — sharing what you saw

Save Snapshot downloads the captured calls as a single self-contained .html file: the trace data, the source file behind every step, and this viewer's own rendering are all embedded. Anyone can open it in a browser — no OCCAS, no login, no network — and see the same timeline and marked source lines you saw. Attach it to a ticket or email; it stays readable long after the trace buffer is gone.

Load Snapshot opens a saved file back in the live viewer (Refresh returns to live data) — the saved file also opens directly on its own, so loading is only needed when you want it side-by-side with live captures.

Saved calls: keeping one on the server

The step buffer is memory: it wraps after 2,000 steps per app and empties on a restart or a redeploy. Save Call keeps the call you are looking at on the AdminServer's host, under its Vorpal-ID, in the directory the savedTracesDirectory setting names (~/.blade/traces unless set, in the home of the user WebLogic runs as). Each call is a folder holding its steps from every app and the source behind them, so the Source tab still shows the code as it ran after that code has changed. Saving the same call again replaces it.

Saved Calls lists them, newest first; pick one to open it, print its report, or delete it. Opening a link of the form traces.html?saved=<Vorpal-ID> opens that call. The folders are readable by their owner only, since a trace holds whole SIP messages, and every open, save and delete is written to the access log.

Snapshots carry source code

A snapshot embeds the application source for every traced step. Share it with the same care as the code itself.

Read-only

This tool never changes configuration — it only displays source and traces, and trace arming is transient runtime state.
