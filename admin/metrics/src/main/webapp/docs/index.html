Metrics

Where the numbers come from

Every BLADE application registers a vorpal.blade:Name=<app>,Type=Metrics MBean when it starts — the same Name key as its Type=Configuration MBean, so the two join on a value this console already has. This page discovers them over the federated DomainRuntime connection and aggregates.

Applications get SIP counters without writing any code: sip.requests by method, sip.responses by status class, sip.errors, and sip.service.time. An app declares its own with a few lines.

How aggregation works, and where it would be wrong

  • Counters sum. Including per-label breakdowns.
  • Gauges sum. Each node reports its own share, so the total is the cluster figure.
  • Histograms merge by bucket. Every node publishes the same boundaries and this console adds the arrays, then computes the percentile from the total.
Why latency is not averaged

Percentiles do not merge. Averaging each node's p95 produces a number that is not a percentile of anything, and taking the worst node's is a different metric wearing the same label. Summing the bucket arrays reconstructs the real distribution, which is why the wire format carries buckets rather than percentiles alone.

If a node reports different bucket boundaries — a rolling upgrade, most likely — its samples are excluded and the histogram is flagged, rather than summed into a plausible but wrong distribution.

What this is not

Not a time-series database. There is no query language, no dashboard builder and no retention: this reads live counters and displays them. Long-term history belongs in a warehouse, fed through an export.

Cost

Counting is a LongAdder increment on a handle resolved once at startup — no map lookup, no string building, no allocation on the call path. Reading is one JMX call per app per node per refresh, which is why the refresh interval is a setting: a short interval on a large cluster is real work on the AdminServer, not on the engines.

Troubleshooting

An app is missing

It registers its MBean at startup, so an app that has not restarted since the framework was upgraded will not appear. Check the Configurator — the app's Type=Configuration MBean exists whether or not its metrics one does.

Counters exist but are all zero

The app registered but has handled nothing. SIP counters only move when messages arrive.

A label reads (other)

Something used a label value the counter did not declare. Label spaces are finite by design — an unbounded one, keyed by a Call-ID or a phone number, is what turns in-process metrics into an outage — so undeclared values are bucketed rather than allowed to grow. The app logs the first occurrence.
