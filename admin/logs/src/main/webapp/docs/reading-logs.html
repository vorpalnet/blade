Reading Log Files

Listing logs

Once a server is selected, the viewer calls GET api/servers/{name}/logs. The response is a list of log file descriptors: 

[
  {
    "relativePath": "AdminServer.log",
    "sizeBytes": 1284733,
    "lastModifiedMs": 1742480123000,
    "kind": "WLS_SERVER"
  },
  {
    "relativePath": "AdminServer-diagnostic.log",
    "sizeBytes": 92340,
    "lastModifiedMs": 1742479000000,
    "kind": "WLS_DIAGNOSTIC"
  },
  ...
]
relativePath
Path relative to the server's log directory. The viewer uses this as the URL path component for reads — slashes are allowed (and the JAX-RS path is {path:.+} to accept them).
sizeBytes
Current file size. Used to compute "where is the end" for tail reads.
lastModifiedMs
Last-modified time. Useful for sorting most-recently-written first.
kind
Coarse-grained classification (server log, access log, diagnostic, GC log, etc.). Drives UI grouping or filtering if added later.

Reading a slice

The read endpoint is GET api/servers/{name}/logs/{path:.+}?offset=N&max=M. The response body is plain text (the bytes of the slice as UTF-8). Three response headers describe the slice:

X-Log-NewOffset
Byte offset to use for the next read to continue from where this one left off. Use this for follow-mode polling.
X-Log-EofReached
true if the slice reached the current end of file.
X-Log-TruncatedAtStart
true if the requested slice was clipped at the start (e.g. offset=-1 tail of a file smaller than max).

Tail mode

Pass offset=-1 to read the last max bytes of the file — standard tail -c semantics.

offset=-1&max=0 is the cheap "how big is this file right now" probe. It is not a special case: the window starts at the end, reads nothing, and reports the current length in X-Log-NewOffset. The viewer uses it instead of re-listing the directory.

Why bytes, not lines

Lines are a rendering concern; the wire protocol is bytes. That keeps a slice deterministic and avoids questions like "how do you tail N lines of a file with 300-character lines?" It also means the client, not the server, decides where a window begins and ends.

Trimming a window to whole lines

A window cut at an arbitrary byte offset starts and ends mid-line, and — more awkwardly — possibly mid-character. The viewer therefore fetches each slice as an ArrayBuffer, scans the bytes for 0x0A, discards the partial line at each end, and only then decodes.

Order matters here. Because the trimmed window always begins and ends just after a newline, it can never split a multi-byte UTF-8 character, so the decode that follows is always safe. Decoding first and trimming the resulting string would have corrupted the edges before anything got the chance to fix them, and would also break the byte arithmetic: the start of a window is X-Log-NewOffset minus the response's byte length, which a decoded string can no longer tell you.

Two edges are already real boundaries and are left alone: byte 0, and end-of-file. A caller extending a window upward also suppresses the end trim, because it requested exactly [start - n, start) and trimming that end would leave a gap between the new chunk and the one it has to join.

Lines longer than a window

If a window contains no newline at all there is nothing to trim to, so the request is retried once, eight times larger, up to the reader's 1 MiB ceiling. Should that still fail, the window is trimmed to a character boundary instead. Half a line is honest; a replacement glyph reads as a bug in the viewer.

Following a live file

Follow mode has its own endpoint, GET api/servers/{name}/tail/{path:.+}?cursor=N&max=M, rather than reusing the slice route. The difference is what happens when the file rotates: the reader treats a cursor past end-of-file as a new file, restarts from byte 0, and reports it in X-Log-TruncatedAtStart. A slice would clamp silently to the new length and the viewer would redisplay the same bytes forever.

  1. Seed the pane with offset=-1 on the slice route.
  2. Poll tail with cursor set to the end of what you hold.
  3. If X-Log-TruncatedAtStart is true, the file rotated — reload from the beginning.
  4. Otherwise advance the cursor only to the last newline received.
  5. Loop.

Step four is the one that is easy to get wrong. Bytes after the last newline are a line the writer has not finished; consuming them renders half a line that never completes. Leaving the cursor short re-reads those few bytes on the next poll, by which time the line is whole.

Searching

GET api/search/{name}/{path:.+}?q=…&regex=…&from=N scans on the node that holds the file, so only matches cross the wire. Each match carries the byte offset of its line, which is what lets a result list steer the viewer instead of duplicating it.

A pass is bounded by both maxMatches and maxScan — the file may be gigabytes and the node is carrying calls. When complete is false, resume from nextOffset. The default treats q as literal text; regex is opt-in, and is matched against a bounded prefix of each line so a pathological pattern cannot run away.

Search needs a restarted node

The VorpalLogReader in a JVM is registered by the first BLADE application to start there and is deliberately left registered when an application stops, so redeploying does not replace it — only restarting the server does. A node that has not restarted since search was added to the MBean will not have it. The endpoint answers supported: false with that explanation rather than failing; it checks MBeanServer.getMBeanInfo, which works against readers built before the method existed.

Downloading

GET api/download/{name}/{path:.+} streams a whole file as an attachment, one MiB per JMX call, with nothing buffered on the AdminServer. Its length is fixed at the size observed when the request starts, which is the right meaning for a download — you get the file as of now, not a tail that never ends on a busy server.

Download and search sit under their own path prefixes for a reason beyond tidiness: servlet security constraints match by path prefix, so a query flag on the slice route could not be held to a narrower role set. A prefix can.
