			How the CRUD service works
			
		
    
		
    
			
    
				
    The pipeline
    
				
    When a call arrives, the CRUD service has to answer one question before it can
				transform anything: which rule set applies to this call? The pipeline answers
				it. It is an ordered list of connectors that each pull values out of
				somewhere and store them as named variables. Selection happens when
				one of them writes the variable named ruleSet — its value names an entry
				in your rule sets. If nothing writes it, the default rule set applies;
				with no default either, the call passes through untransformed.
    
				
    The everyday shape is two connectors: a sip connector that extracts a
				value from the message (say, the dialed number from the To header), then a
				table connector that looks that value up and writes ruleSet.
				That's the whole trick — everything else is optional power.
    
				
    Every variable the pipeline extracts is also available inside rule operations as
				${name}, so the pipeline does double duty: selection and data
				gathering.
    
			
    
			
    
				
    Connector types
    
				
    sip — reads the SIP request itself; no I/O. Its selectors pull
				headers, the Request-URI, the body, or transport facts (originIP,
				transport, …). Almost every pipeline starts with one.
    
				
    table — looks a variable up in one or more translation tables and
				spreads the matched row's values into variables. First table that matches wins. This is
				the usual place ruleSet gets written.
    
				
    rest / jdbc / ldap — fetch enrichment data from an external service,
				database, or directory, then run selectors over the response. These do real I/O
				inline on the call path, so every millisecond they take is added to INVITE
				processing — prefer message-derived selection when you can.
    
			
    
			
    
				
    Selectors
    
				
    A selector pulls one value out of whatever its connector produced and stores it
				under the selector's id — that id is the variable name you reference
				later as ${id}.
    
				
    attribute takes a value verbatim (a header, a map field).
				regex matches a pattern with named groups —
				(?<user>[^@]+) — and stores each named group as its own variable,
				plus an optional rendered expression template under the selector's id.
				json / xml / sdp extract by JsonPath, XPath, or SDP field from a
				payload. table classifies an already-extracted value through a
				translation table.
    
			
    
			
    
				
    Translation tables and match strategies
    
				
    A table has a keyExpression (a ${var} template
				that produces the lookup key), a match strategy, and rows. The strategies:
				hash is an exact match; prefix is longest-prefix
				(dial plans: row 1816 matches key 18165551234);
				range matches integer intervals (row 8-17 matches key
				9 — time-of-day buckets, score bands). Each row's values all become
				variables when it matches; a row with a ruleSet column is what makes
				selection happen.
    
			
    
			
    
				
    Rule sets, rules, and filters
    
				
    A rule set is an ordered list of rules. In an application's own crud
				section a rule runs on every message the application sends (send), and,
				only if its event names receive, on every message it receives,
				before the application handles it. The CRUD service runs rules at points in the call's
				life instead: callStarted, callAnswered,
				callConnected, callCompleted, and in-dialog traffic
				(requestEvent / responseEvent). Every rule whose filters all
				pass runs its operations, in order.
    
				
    An empty filter matches everything. method and event accept
				comma-separated alternatives and ! negation (INVITE,REGISTER,
				!BYE). statusRange matches response codes: 200-299,
				4xx, !5xx; setting it limits the rule to responses.
				leg picks the side of a B2BUA the message is on: caller or
				callee. sdp picks messages carrying an SDP offer or
				answer, wherever the offer/answer exchange puts it: an INVITE, a re-INVITE, an
				UPDATE, a 2xx to an INVITE without SDP, an ACK, a PRACK. when is a boolean
				expression over variables: ${customerTier} == premium, with
				== != < > && || ! plus
				matches (regex), contains, and insubnet (CIDR). A
				malformed when never fires the rule.
    
				
    A rule is all or nothing. If one of its operations fails, the message and the
				variables go back to how they were before the rule ran, and the next rule runs as usual.
				An operation with nothing to do (no such header, a variable with no value) is not a
				failure.
    
				
    Rules are keyed by id and run in the order written. In a cluster or server file, a
				rule with an inherited id changes that rule: its fields replace the inherited ones and
				its operations run after them. off switches a rule off, which is how such a
				file removes one. A new id runs after the inherited rules.
    
			
    
			
    
				
    Operations: where the name CRUD comes from
    
				
    CRUD = Create, Read, Update, Delete, the four verbs a rule can apply
				to any part of a message. create adds a header occurrence, body part, or
				node; read captures values into variables; update
				rewrites in place; delete removes. Each verb comes in four addressing
				modes: the plain family addresses SIP headers, the Request-URI, the response
				status and reasonPhrase, and the raw body by regex; the
				xml* family uses XPath; json* uses JsonPath; sdp*
				uses JsonPath over the SDP parsed to a structured model ($.media[0].port,
				$.media[?('inactive' in @.attributes[*].name)]). Multipart MIME bodies are
				handled part by part: target one part by content type, the rest ride through.
				keepPart strips a multipart down to one part.
    
				
    A header can appear more than once. read takes the first occurrence
				its pattern matches, update changes each occurrence it matches and
				leaves the rest, create adds another occurrence, and
				delete with a pattern removes only the occurrences it matches.
				update replaces the whole value unless everyMatch is set,
				which replaces each match in place.
    
				
    Writing status turns one failure into another (300 to 699,
				such as 486 into 480, but never a 4xx-6xx into a redirect, which needs a Contact); an answered call cannot become a failure. reject
				refuses an initial INVITE: the caller gets the status you give, and the INVITE goes no
				further. Messages inside a call cannot be refused, since the other end would never
				learn of it.
    
				
    Values, regex patterns, JsonPaths and XPaths support ${var} from
				everything read so far: pipeline variables, read captures, plus ${now} and
				${uuid}. A value goes in as data, never as syntax: quoted in a regex, escaped
				in a JsonPath string (write '${var}'), a whole string literal in an XPath
				(write ${var} bare). A variable with no value skips the operation, so
				${var} never goes out on the wire. Environment variables and system
				properties are used only when named: ${env:NAME},
				${sys:NAME}.
    
				
    The remove-and-restore trick: an sdpRead of a filter path saves whole
				media blocks in a variable; a later sdpCreate with parent
				$.media and value ${thatVariable} splices them back. That's the
				minsdp pattern.
    
			
    
			
    
				
    Preview, Save, Publish
    
				
    The preview always runs your unsaved draft: Auto-select runs the draft
				pipeline and reports which rule set it picks (and fills Inputs with what it
				extracted); Run replays the message through a rule set and shows the before/after diff,
				which rules fired, and any warnings the engine logged. Nothing touches the wire.
    
				
    Save validates the document exactly as the CRUD service would load
				it, and also compiles every when, status range, regex, XPath and JsonPath,
				which at run time would only fail quietly on a live call. Problems are listed under
				the toolbar, and every preview refreshes that list. Save keeps the previous file in version history, and writes crud.json.
				Publish is the separate act that tells the running service to reload
				what was last saved; beside it, running says whether every server running this
				file holds what was saved. Logging and session settings are edited in the Configurator;
				both tools share the same file.
    
			
    
			
    
				
    Variables and the three files
    
				
    variables are values every call starts with: the pipeline, when
				and operations read them as ${name}, and a connector may overwrite one.
				Use them for what differs between servers (a carrier host, a trunk prefix), so a
				server file sets one value instead of changing rules.
    
				
    An application has up to three files, listed beside the page: the domain file, a
				cluster file, a server file. A server runs them merged in that order: variables,
				connectors and rules merge by name, so a lower file changes one by naming it, and a new
				name is added after the inherited ones. A rule switched off stops running; in the
				JSON, null removes an inherited rule, connector or variable. merged (read-only) shows what a file runs, with the file that set
				each line.
    
			
    
			
    
				
    Tests and traced calls
    
				
    Save as test keeps the last preview's inputs and its result: whether it was
				refused, and the whole output message. Saving the domain file runs the domain's tests
				and refuses on a failure, naming the first line that differs; update accepts
				an intended change. A cluster or server file keeps its own tests, run with Run
				tests. Tests are stored in _tests/<app>.json beside the
				configuration, and never reach an engine.
    
				
    A traced call lists calls the Callflow trace captured for this application:
				load one message into the preview, or run the whole call in order, carrying what each
				run sets to the next. Arm a trace in Callflow first. Each rule's hits count
				the messages it matched on the running servers since the application was deployed.
    
			
    
			
    
				
    Rules inside an application
    
				
    A v3 application carries the same rules in a crud section of its own
				configuration and runs them on every message it sends, so a header change no longer
				needs the CRUD service chained in front of it. Pick the application in
				Rules for. Save writes only that section back into
				<app>.json; the rest of the file is left as it was.
    
				
    These rules see one lifecycle event, send. Leave a rule's
				event empty and choose by method, message type, status range and
				when. The pipeline runs once, on the call's first request, and most
				applications need none: the default rule set applies to every call.
