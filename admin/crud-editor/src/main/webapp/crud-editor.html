			How the CRUD service works
			
		

		

			

				
The pipeline

				
When a call arrives, the CRUD service has to answer one question before it can
				transform anything: which rule set applies to this call? The pipeline answers
				it. It is an ordered list of connectors that each pull values out of
				somewhere and store them as named variables. Selection happens when
				one of them writes the variable named ruleSet — its value names an entry
				in your rule sets. If nothing writes it, the default rule set applies;
				with no default either, the call passes through untransformed.

				
The everyday shape is two connectors: a sip connector that extracts a
				value from the message (say, the dialed number from the To header), then a
				table connector that looks that value up and writes ruleSet.
				That's the whole trick — everything else is optional power.

				
Every variable the pipeline extracts is also available inside rule operations as
				${name}, so the pipeline does double duty: selection and data
				gathering.

			

			

				
Connector types

				
sip — reads the SIP request itself; no I/O. Its selectors pull
				headers, the Request-URI, the body, or transport facts (originIP,
				transport, …). Almost every pipeline starts with one.

				
table — looks a variable up in one or more translation tables and
				spreads the matched row's values into variables. First table that matches wins. This is
				the usual place ruleSet gets written.

				
rest / jdbc / ldap — fetch enrichment data from an external service,
				database, or directory, then run selectors over the response. These do real I/O
				inline on the call path, so every millisecond they take is added to INVITE
				processing — prefer message-derived selection when you can.

			

			

				
Selectors

				
A selector pulls one value out of whatever its connector produced and stores it
				under the selector's id — that id is the variable name you reference
				later as ${id}.

				
attribute takes a value verbatim (a header, a map field).
				regex matches a pattern with named groups —
				(?<user>[^@]+) — and stores each named group as its own variable,
				plus an optional rendered expression template under the selector's id.
				json / xml / sdp extract by JsonPath, XPath, or SDP field from a
				payload. table classifies an already-extracted value through a
				translation table.

			

			

				
Translation tables and match strategies

				
A table has a keyExpression (a ${var} template
				that produces the lookup key), a match strategy, and rows. The strategies:
				hash is an exact match; prefix is longest-prefix
				(dial plans: row 1816 matches key 18165551234);
				range matches integer intervals (row 8-17 matches key
				9 — time-of-day buckets, score bands). Each row's values all become
				variables when it matches; a row with a ruleSet column is what makes
				selection happen.

			

			

				
Rule sets, rules, and filters

				
A rule set is an ordered list of rules, applied at every point in the call's life —
				the outbound INVITE (callStarted), the answer (callAnswered),
				the ACK (callConnected), the BYE (callCompleted), and
				in-dialog traffic (requestEvent / responseEvent). Every rule
				whose filters all pass runs its operations, in order.

				
Filters are null-tolerant — an empty filter matches everything. method
				and event accept comma-separated alternatives and ! negation
				(INVITE,REGISTER, !BYE). statusRange matches
				response codes: 200-299, 4xx, !5xx — setting it
				implicitly limits the rule to responses. when is a boolean expression over
				variables: ${customerTier} == premium, with
				== != < > && || ! plus
				matches (regex), contains, and insubnet
				(CIDR). A malformed when never fires the rule.

			

			

				
Operations — where the name CRUD comes from

				
CRUD = Create, Read, Update, Delete — the four verbs a rule can
				apply to any part of a message. create adds a header, body part, or
				node; read captures values into variables; update
				rewrites in place; delete removes. Each verb comes in four addressing
				modes: the plain family addresses SIP headers, the Request-URI, and the raw body by
				regex; the xml* family uses XPath; json* uses JsonPath;
				sdp* uses JsonPath over the SDP parsed to a structured model
				($.media[0].port,
				$.media[?('inactive' in @.attributes[*].name)]). Multipart MIME bodies
				are handled part by part — target one part by content type, the rest ride through —
				and keepPart strips a multipart down to one part.

				
Values support ${var} substitution from everything read so far
				— pipeline variables, read-operation captures, plus ${now} and
				${uuid}. The remove-and-restore trick: an sdpRead of a
				filter path saves whole media blocks in a variable; a later sdpCreate with
				parent $.media and value ${thatVariable} splices them
				back — that's the minsdp pattern.

			

			

				
Preview, Save, Publish

				
The preview always runs your unsaved draft: Auto-select runs the draft
				pipeline and reports which rule set it picks (and fills the variables grid with what it
				extracted); Run replays the message through a rule set and shows the before/after diff,
				which rules fired, and any warnings the engine logged. Nothing touches the wire.

				
Save validates the document exactly as the CRUD service would load
				it, keeps the previous file in version history, and writes crud.json.
				Publish is the separate act that tells the running service to reload
				what was last saved. Logging, session settings, and per-cluster overlays are edited in
				the Configurator — both tools share the same file politely.
