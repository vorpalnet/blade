Overview

The CRUD service

CRUD is the classic data acronym — Create, Read, Update, Delete — and the service earns the name literally: those are the four verbs a rule can apply to a SIP message. Create adds something that wasn't there (a header, a body part); Read captures a value into a variable for later rules to use; Update rewrites in place; Delete removes.

Each verb works on any form of message data. The plain operations address SIP headers, the Request-URI, and the raw body by regular expression; the xml operations address XML bodies by XPath; the json operations address JSON bodies by JsonPath; and the sdp operations address SDP — parsed to a structured model, so $.media[0].port means the first media line's port, not a lucky text match. Multipart MIME bodies are handled part by part: an operation targets one part by content type and the others ride through untouched.

The service itself is a B2BUA that applies the selected rule set at every point in a call's life — the outbound INVITE, the answer, the ACK, the BYE, and in-dialog traffic. The rules are data, not code; a new transformation is a config change, not a deployment.

The three-step model

The editor presents the service's configuration the way the service itself thinks:

1 · Pipeline
Decides which rule set each call gets. Connectors run in order on each initial request, extracting values from the message into variables; selection happens when one of them writes the ruleSet variable. Unmatched calls take the default rule set, or pass through untransformed.
2 · Rule sets
Say what happens to the selected calls. Each rule filters by method, lifecycle event, status range, or a when expression, then runs its operations in order.
3 · Preview
Proves it. Paste a real SIP message and the editor replays your unsaved draft through the same engine production runs — Auto-select shows which rule set the pipeline picks; Run shows the before/after diff, the rules that fired, and the variables captured.

Division of labour with the Configurator

This editor owns the CRUD-specific sections of crud.json: the pipeline, the default rule set, and the rule sets. Logging, session settings, and per-cluster/per-server overlays stay in the Configurator. Both tools read and write the same file; each leaves the other's sections untouched.

Save and Publish are separate acts

Save validates the document exactly as the CRUD service would load it — a config the service couldn't parse is rejected with the parse error — then writes crud.json, keeping the previous version restorable from the Versions panel. Publish tells every node running the CRUD service to reload what was last saved. Nothing reaches the wire until you publish.

Forms follow the schema

Every form in the editor — connectors, selectors, operations — is generated from the service's own JSON Schema. When the framework grows a new connector or operation type, it appears in the editor without an editor change.
