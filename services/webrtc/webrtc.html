BLADE · services/webrtc

Browser-to-SIP communication.

On the browser side, the gateway speaks a simple JSON protocol over a WebSocket; on the network side, standard SIP. It sits in the middle and translates between the two. When two browsers call each other, their audio flows directly between them and no media server is needed. A media server joins only when a call reaches a traditional phone, or when something downstream needs access to the audio.

Why this matters

Oracle shipped WebRTC Session Controller once, then discontinued it.

The BLADE gateway brings that capability back on OCCAS — without the three things that made the original hard to live with.

1 · the translation

No custom scripting.

With WSC, every deployment had to hand-write and maintain the code that translated between the browser and SIP.

Here that translation is built into the gateway — written and tested once, the same for everyone.

2 · the media plane

No locked-in media server.

WSC handed the media plane to the ASC, an end-of-life product that took copious, poorly-documented configuration to get working at all.

This gateway reaches the media server through a vendor-neutral interface — the choice stays open, and no vendor is named in the product.

3 · the client

A current browser client.

The old client was written against browser features that no longer exist. The BLADE softphone is built to today's standards.

The central rule

Every call is a real SIP call.

The signaling always runs over SIP, even when both parties are browsers. A browser-to-browser call gets the same routing, logging, and analytics as any call between two phones — an operator manages it with the tools they already have.

What varies from one call to the next is the path the audio takes. One setting, mediaMode in webrtc.json, controls it:

  • Relay — the two browsers send audio straight to each other, with no media server in the middle. All a browser-to-browser call needs.
  • Anchor — the audio passes through a media server. Required when one end is a regular phone, or when a system downstream needs the audio for recording, conferencing, or transcription.
  • Auto (the default) — relay between browsers, anchor when a phone is on the call, decided per call.

End-to-end encryption

Relayed calls are private end to end.

  • The two browsers complete a DTLS handshake directly with each other and derive their SRTP keys from a master secret the signaling path never sees. The gateway forwarded fingerprints and nothing more, so it cannot decrypt a single packet.
  • The same is true for anything downstream. Recording, transcription, and monitoring each belong to a separate service — but none can reach a relayed call either, because the audio never leaves the two browsers.
  • Anchoring is the only thing that puts a call's media somewhere another system can use, which is why the choice lives here even though the features do not.
  • A relayed call can still be moved onto a media server afterwards, by re-INVITE. It costs an ICE restart and a fresh DTLS handshake, so there is a brief audible gap. Anchoring from the start avoids that and pays for a media server on every call — that trade is the whole reason the setting exists.

In-dialog

Re-INVITEs are handled on both media paths.

A far end re-offers for ordinary reasons — hold, unhold, a session refresh, a codec change — and every one is handled. The gateway watches for a re-offer from the moment a call is answered, and keeps watching, because a call is re-offered repeatedly.

How the gateway responds depends on which media path the call is using:

Anchored
  • The re-offer belongs to the network dialog alone. The media server answers it and the browser is never told, because the two negotiations were independent from the start.
  • A no-SDP refresh is answered from the media server, with the answer taken from the ACK.
Relayed
  • The browser owns both halves, so the SDP goes to it as call.update and its answer becomes the 200 OK. This is also how a far-side escalation — an upgrade to video — reaches the browser.
  • A re-INVITE with no SDP is refused 488 here and only here: it asks this gateway to produce an offer, and without a media server there is nothing to produce one with — a browser cannot be made to offer on demand.

In-dialog

Two more things that happen mid-call.

A caller who hangs up while ringing

If the caller gives up while the browser is still ringing, the call arrives as a SIP CANCEL. The gateway stops the ringing, releases any media, notifies the browser, and records the call as abandoned — but sends no response of its own.

The container handles that transaction itself: it answers the CANCEL and terminates the original INVITE with a 487. Were the application to answer as well, a second final response would go out on the wire, so the framework suppresses the duplicate.

DTMF travels over signaling, not audio

call.dtmf becomes a SIP INFO carrying application/dtmf-relay toward the far end.

It does not inject a tone into the audio stream — no JSR-309 media driver behind the framework generates tones, so that route isn't available. Carrying the digit over signaling works the same on both media paths: a relayed call has no media session to inject into, and the INFO rides the SIP dialog either way.

Not SIP over WebSocket

RFC 7118 exists and works. OCCAS does not implement it.

  • The JSR-359 interfaces ship in the API jar.
  • The container behind them has no WebSocket transport, and the only network channels it offers are sip and sips.
  • So a browser cannot register as a SIP UA against this server regardless of how the application is written.

And it happens to match the design we would have chosen anyway.

A browser answering "a call is arriving, do you want it?" has no need to own dialogs, Via headers, registration refreshes or transaction state.

The protocol

Two verbs were defined early and then deliberately removed.

call.accept

Meant "yes, without SDP".

There is no SIP message it can honestly produce: both answer paths build the 200 OK from an SDP only the browser has.

call.answer is a moment away and does the job properly.

call.record

A browser asking this gateway to record.

Recording belongs to a service of its own.

What the gateway owes such a service is the one decision only it can make — whether the call's media is anchored at all — and that is mediaMode, a configuration field, not an event.

The protocol

Answered and connected are two events, because SIP answers a call in three messages.

call.established is the 200 OK. call.connected is the ACK that completes the handshake, and never arrives before it.

The split follows the framework's own call lifecycle — CALL_ANSWERED then CALL_CONNECTED — and it exists because the third message carries information.

  • negotiated is false when the far end answered with no SDP and nothing was applied to the media dialog: a call that is up for signaling and silent for media.
  • Previously that case was reported as an ordinary call.established and looked healthy.
  • call.connected also declares an sdp field, reserved and unset on every path today. The ACK is a real SDP-carrying moment — in late media the caller's answer arrives there — so the field is declared to describe the message honestly. Clients must tolerate its absence, which is the ordinary case.
  • call.update is the one that makes escalation possible: a fresh SDP offer for a call already up. Without it a call's media path could never change after setup — the same mechanism WSC's mobile SDKs exposed as Call.update().

The protocol · two behaviours worth knowing

Complete SDP both ways, and the browser is answered during alerting.

ICE is not trickled
  • A browser sends its whole offer or answer after gathering finishes, candidates included, and the gateway forwards SDP whole.
  • Anchored: because the media server does not advertise inbound trickle.
  • Relayed: because the SDP crosses a SIP fabric whose forks and B2BUA hops have no channel for mid-flight candidates.
  • Sending complete SDP also removes a class of ordering bugs from the client. The ice.candidate type remains — the gateway may still trickle its own candidates toward the browser on anchored calls.
Answered during alerting
  • On an anchored outbound call call.progress carries the gateway's SDP answer, so the browser has a media path while the far end is still ringing.
  • Deferring it to call.established would mean no ringback and no carrier early media.
  • On the relayed path there is no local answer to give early: the far end's SDP is forwarded as it arrives — on call.progress when an 18x carries it, else on call.established — and exactly once, because a browser cannot apply a second answer.

Authenticating a browser

A socket arriving here says nothing about who is on the other end.

It comes from a page on a different server and port, so no admin cookie reaches this tier and the WebSocket handshake carries no Authorization header. Left alone, "who are you?" is answered by whatever the client claims — so session.connect carries a signed token, and BrowserAuthenticator decides.

Authentication fails closed.

  • Missing or unusable configuration — a blank or unreachable jwksUri — refuses the browser and names the setting to fix. "We could not read the rule" must never mean "there is no rule."
  • The only open path is explicit: jwt.enabled = false lets any browser claim any address, logs SEVERE at startup, and reports authenticated: false in session.ready.
  • The shipped sample pairs enabled = true with a blank jwksUri, so a half-configured deployment refuses to work rather than running open.

Location service

The gateway REGISTERs on the browser's behalf.

BrowserRegistry is only the socket table — which browsers hold a live WebSocket on this node. The network's location service is proxy-registrar, and browsers appear in it because the gateway speaks SIP for them — the same arrangement a session border controller uses.

  • That contact is the whole inbound routing story. The registrar stores it verbatim and forks the INVITE to it; the container dispatches the call into the registration's session before the router runs.
  • No FSMAR rule names this app for inbound calls — the REGISTER said everything.
  • So BrowserRegistry being node-local is not a cluster limitation. A 480 means the binding is stale — the browser has not re-registered yet.

Location service · lifecycle

Bindings lapse, so a timer renews them — and stops when the socket does.

  • It refreshes at the expiry the registrar granted, not the one requested, since a registrar may shorten a binding and refreshing on the asked-for value would let it lapse early.
  • The timer stops when the socket does. If the browser is no longer connected to this node, the refresh cancels itself rather than re-asserting a contact naming an engine that can no longer deliver. Letting the binding lapse is the honest outcome; a browser that comes back registers again from wherever it lands.
  • On socket close or error the gateway sends Expires: 0. A page reload never tears down its successor's binding: the superseded socket's unregister returns null, and the replacement's re-REGISTER refreshes the same binding.
  • Registration is best-effort — a REGISTER failure logs a WARNING and the browser keeps its session.
  • One call at a time per browser follows from the session-per-AOR shape: inbound targeted calls land on the registration's session, so a second simultaneous INVITE for the same AOR would collide with the first's continuations. A browser tab is a one-call phone — the honest shape, not a limitation.

Late media

An INVITE with no SDP — the case the earlier product dropped.

  • This is the one path where call.established and call.connected are genuinely far apart, and the only one where the ACK can arrive owing an answer it does not carry — hence negotiated: false.
  • Late media always anchors, and cannot be made to work without a media server. Having the browser offer instead was considered and rejected: late media is a pattern browsers never originate, so the caller is a phone or a trunk, and the answer coming back in the ACK is plain RTP with no DTLS fingerprint — which a browser will not set up media against.
  • On this call shape the media server is the only party present that can speak to both ends. Without a driver the gateway refuses with 503 and says so by name in the log.

What a call reports to analytics

A browser call is a call, to everything downstream.

A WebRTC call used to be invisible to analytics — none of the framework's own publishers ever ran for it, and a browser call left no trace in any report.

Reusing them is the point: one subscription gets browser calls and phone calls together, with no webrtc-specific clause.

  • Every fact carries a dialog attribute, inbound or outbound. A browser-to-browser call is one call that crosses this application twice — out and back in through the location service — and the second dialog inherits the first's correlation id. Both publish under the same correlator, source and application name; dialog is the only thing that tells them apart.
  • analytics.enabled is the switch, not events.enabled. Setting events.enabled alone gives a live bus connection carrying no call facts.
  • The shipped sample fills in the selectors and leaves the switch off, the way every other BLADE application samples itself.

Deployment requirements

Four things, and two of them fail quietly.

  • A reachable STUN or TURN server is mandatory, not optional. Since Chrome 76 browsers publish <uuid>.local mDNS host candidates instead of private addresses; without a server-reflexive path there is frequently no routable candidate pair. This is the most likely cause of "works on a laptop, fails on OCI".
  • Set the media node's public address. On OCI the instance cannot see its own public IP, so the provider must be given external.ipv4 or it will advertise an unreachable candidate. Both of these apply only to anchored calls — a relayed browser-to-browser call needs neither.
  • Media-plane settings live in webrtc.json under driverProperties and are handed to the JSR-309 driver verbatim; driverName picks between drivers when more than one is installed. Both are read once, at deployment — republishing configuration does not rebuild the factory, so a change needs a redeploy.
  • The driver jar has to be visible to this WAR. Skinny-WAR policy keeps everything but the framework out of WEB-INF/lib, so driver jars go in the blade-shared shared library or the domain's lib/. Without it the servlet says so plainly: browser-to-browser still works, calls to phones do not.

The browser client is a separate app

The gateway ships no client — so you can build your own.

  • This WAR is Java only — it serves no page and ships no script. The browser side, both the client library and the softphone UI, is admin/phone: a separate static app on the admin tier that connects here at /webrtc/signal.
  • Keeping them apart is deliberate. A gateway that served its own client would carry a second copy of the protocol to keep in sync, and would tie the UI to the engine tier. As a static page, the softphone can be hosted anywhere.

The bundled phone app is one worked example of a WebRTC client — not the only way to build one.

The protocol is plain JSON over a WebSocket, so a customer can build their own client against it — in JavaScript for the browser, or natively for iOS or Android.
